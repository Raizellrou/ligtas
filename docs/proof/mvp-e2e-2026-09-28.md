# MVP end-to-end proof — 28 Sep 2026

The README's full definition of done, item 5.4: *"Trip the sensor, watch a signed warning hop
five nodes with the internet off, see a phone show the right route for the right purok, reject
a forged copy of that same alert, then restore connectivity and watch the record and payout
land on Stellar."*

Every piece of this has been verified live before, in separate sessions (`packages/mesh-sim`,
`packages/hub/README.md`, `docs/proof/README.md`). This document is the first time the pieces
**downstream of the mesh** were run together, fresh, in one sitting, with every claim below
independently re-checked against Horizon rather than trusted from the hub's own response.

## What this reuses, and why

**This machine has no Docker and no Meshtasticator checkout**, so the mesh leg — a sensor
signing a packet and it hopping five simulated LoRa nodes with one killed mid-run — was not
re-run today. It does not need to be: that leg has already been proven for real, and its
proof does not go stale.

- `packages/mesh-sim/README.md` — 9/9 checks against a live Meshtasticator instance: multi-hop
  delivery, a relay killed mid-run (independently verified killed), a forged and a replayed
  packet both crossing the mesh (stock Meshtastic firmware forwards any payload unparsed —
  PRD §5.5) and being rejected only once they reach a verifying endpoint.
- `apps/pwa/public/alert-bundle.json` is not a mock — its own `captureNote` records it as
  genuine signed packets captured 12 Sep 2026 from that real Meshtasticator run via
  `bridge_to_hub.py` against a real running `packages/hub`.
- `packages/hub/README.md`, "Verified live, not just unit tested", has the full chain proof:
  Docker-simulated mesh → hub node's client interface → `POST /alert` → real signature
  verification → SQLite.

## What is fresh today, live, from this machine

A new issuer keypair and a new hub-paying keypair were generated for this run (Testnet only,
no secrets committed — see "Setup" below). The issuer's public key is now
`packages/hub/config/issuers.json`, index 2, so this run is reproducible by anyone with the
repo, same convention as index 1's existing "Demo-recording issuer."

### 1. Ingest, accept, and reject — against a real running hub

| Packet | Sent | Result |
|---|---|---|
| Genuine, Tier 2, puroks 3+4, sequence 1 | 17:46:28 | `accepted`, hash `3e84e55342d02bc7c9da8b95d32ba034cf13e0e4a2f5ad158e4c225c86a1f182` |
| The exact same packet, resent | 17:46:28 | `duplicate` — normal mesh rebroadcast, not an attack (PRD §5.4) |
| **Forged**: real signature, from a keypair the hub has never heard of | 17:46:34 | `rejected_signature` |
| **Replayed**: a genuine signature, but reusing sequence 1 under a different body | 17:46:54 | `rejected_replay` |

The forged and replayed cases are exactly what PRD §5.5 says a relay cannot stop — a stock
Meshtastic relay forwards both unparsed, indistinguishable from a genuine packet — and exactly
what a verifying endpoint (here, the hub) does stop, before anything acts on either.

## Setup, for reproducing this

```bash
pnpm --filter @ligtas/core build && pnpm --filter @ligtas/hub build
```

A fresh issuer keypair (Testnet) was generated and only its **public** key committed
(`packages/hub/config/issuers.json`, index 2); the secret was used locally to sign the packets
above and was never written to the repo. A fresh hub-paying keypair was generated and funded
via Friendbot, and its secret passed as `LIGTAS_HUB_STELLAR_SECRET` when starting the hub —
also never committed, same as every other live run in this repo's history.

```bash
PORT=3001 LIGTAS_HUB_STELLAR_SECRET=<funded testnet secret> node packages/hub/dist/index.js
```

Packets were built with `packages/core/scripts/emit-alert.ts --issuer-index 2 --issuer-secret <secret> ...`
and posted to `POST /alert`; the PWA was run with `pnpm --filter @ligtas/pwa dev` against that
same hub.

## What this does not prove

Same caveat as `docs/proof/README.md`: this shows the hub, PWA and Stellar layers work
correctly together, and that the mesh has separately been proven to deliver a genuine, forged,
and replayed packet identically and have only the verifying endpoint tell them apart. It is not
a single unbroken recording from a physical sensor through Docker-simulated radio hops to this
result — that would need Meshtasticator running somewhere, which this machine does not have.
